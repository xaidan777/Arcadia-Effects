# AFX Ядро: симуляция, рендер, данные

## Детерминизм (главный инвариант)

- Симуляция идёт фиксированным шагом `DT = 1/120` (sim.js) от t=0 слоя. Перемотка
  назад = `reset()` и пересчёт от нуля — это ДЁШЕВО и правильно, не кэшируй историю.
- RNG — `AFX.mulberry32(seed)`, сидируется в `Sim.reset()` от `layer.em.seed`.
  Число вызовов rng на один spawn обязано быть СТАБИЛЬНЫМ при фиксированном конфиге
  слоя: ветвление по форме эмиттера допустимо (форма постоянна между reset),
  ветвление по данным конкретной частицы — НЕТ.
- Запрещены `Date.now()`, `Math.random()`, любые внешние источники в пути
  sim/engine/atlas. Шум — только детерминированный: `AFX.noise1` (1D), `AFX.noise2`
  (2D), `AFX.noise3` (2D + ось времени), `AFX.turb3` (турбулентный fBm по |шуму|),
  `AFX.curl2` / `AFX.turbCurl3` (бездивергентные вихревые поля). Хэш 2D/3D-шума —
  ЦЕЛОЧИСЛЕННЫЙ (`AFX.hash2`, imul), а не sin: побитово одинаков в любом движке.
- `Sim.ensure(layer, tl)` доводит состояние до узла сетки `<= tl` и возвращает
  остаток для ЭКСТРАПОЛЯЦИИ отрисовки (позиция + vel*ext). Экстраполяция не должна
  менять состояние.
- Инвалидация: любая мутация слоя обязана пройти через `AFX.touch(layerId)` —
  он инкрементит `layer._rev`; `Sim.ensure` сравнивает rev и делает reset.
  Поля с префиксом `_` не сериализуются (`Model.stripJson`).

## Engine

- `AFX.Engine` — класс; у превью, атласа и миниатюр СВОИ инстансы с изолированными
  кэшами симуляций (нельзя шарить: атлас прогоняет время вперёд).
- Порядок слоёв: `doc.layers[0]` — верхний, рисуется последним (итерация с конца).
- Solo: если есть хоть один solo+on слой — рендерятся только solo.
- Координаты: (0,0) = центр композиции. Компрессия `k = cos(cam.comp)` плющит
  ТОЛЬКО render-позиции (y*k) и, опционально, сам спрайт через per-layer `squash`
  (матрица: translate -> scale(1, squashK) -> rotate -> scale). Физика — в мире, без k.
- Свечение частиц: тонированный блюр-спрайт из кэша `S.getGlow(sig, hex, blurFrac)`;
  сила >1 — дополнительные аддитивные проходы (цикл по rem). Всегда blend 'lighter',
  после — вернуть blend слоя.
- РАДИАЛЬНОЕ затухание (`layer.fadeOn` + треки fadeX/fadeY/fadeR + fadeSoft):
  маска destination-in радиальным градиентом по тому же оффскрину, ПРИМЕНЯЕТСЯ
  ДО свечения (ореол тоже гаснет); эллипс по компрессии (scale(1,k)); внутренний
  радиус = r*(1-soft). Путь fadeOn=false && glowL=0 остаётся прямым.
- ПОСЛОЙНОЕ свечение (`layer.glowL` трек 0..3 + `layer.glowLR` радиус px):
  при glowL>0 слой рендерится в оффскрин `Engine.scratch('_layFx')`, композитится
  на комп со СВОИМ blend, затем блюр-копия (`_blurFx`, ctx.filter blur) складывается
  'lighter' мультипроходами. Путь glowL=0 обязан оставаться прямым (без оффскринов) —
  старые эффекты попиксельно неизменны. Для трейлов/молний использовать именно
  послойное свечение — per-particle glow трейла это лишь широкий штрих.

## Турбулентность частиц

- `pt.turbMode: 'noise'` (дефолт) — независимый шум по возрасту КАЖДОЙ частицы.
  Соседние частицы не связаны: получается дрожание, структуры не возникает никогда,
  сколько амплитуду ни крути. Оставлен как есть — старые файлы попиксельно те же.
- `pt.turbMode: 'curl'` — общее вихревое ПОЛЕ в мировых координатах
  (`turbScale/turbOct/turbRise/turbSeed`): соседние частицы читают одну точку и
  уезжают вместе связной струёй. Это и даёт языки, завитки, срывы.
- `turbAmp` — ускорение (px/с²). `turbWind` — то же поле как СКОРОСТЬ СРЕДЫ:
  сопротивление считается ОТНОСИТЕЛЬНО ветра,
  `v = W + (v + a·dt − W)·e^(−drag·dt)` — точное решение `dv/dt = a − drag·(v − W)`
  при постоянном W на шаге. Частицу НЕСЁТ потоком, а не колотит им. Работает только
  при `drag > 0`; при `turbWind = 0` формула тождественно сворачивается в прежнюю.
- `turbRamp` (оба режима) гасит турбулентность у молодых частиц по
  `smoothstep(0.04, 0.34)` доли жизни — ламинарное основание плюма.
- ВАЖНО ПРО ФОРМУ: curl-турбулентность двигает частицы связно, но САМ СИЛУЭТ из
  спрайтов не лепит. Языки пламени режет постэффект `displace` (см. ниже) — возить
  по полю фигурные спрайты бессмысленно, выходит мозаика из одинаковых капель.

## Трейлы, ветвление, зигзаг (молнии)

- `pt.render: 'sprite'|'trail'` — трейл рисует ПУТЬ частицы полилинией
  (история `p.hist`, вершина каждые 2 шага, кап 240 точек): glow-штрих (lighter)
  + основной штрих цветом градиента(lf) + белое ядро `pt.trailCore`. Ширина =
  pt.size * sizeOL(lf) * sizeOT(u), где u — доля длины дуги вдоль пути
  (0 — основание/спавн, 1 — голова). КОНСТАНТНАЯ sizeOT (дефолт 1) идёт старым
  однородным штрихом (старые эффекты попиксельно неизменны), непостоянная —
  заливкой ленты с переменной полушириной (drawTrail/ribbon* в engine.js). История — часть состояния симуляции, детерминирована.
- Ветвление `em.branch` (chance/сек, spread, lifeScale от ОСТАТКА жизни родителя,
  sizeScale, speedScale, maxGen): кубик и параметры ветки берутся из
  СОБСТВЕННОГО prng частицы (`hash01(stepN, p.seed)` + `mulberry32(seed+stepN)`),
  ОСНОВНОЙ поток rng слоя не трогается — старые эффекты попиксельно неизменны.
  Дети пушатся в конец массива и в текущем шаге не итерируются (обход с конца).
  Жёсткий кап MAX_PARTS действует и на ветки.
- `pt.zigzag` (град/с) — покадровый БЕЛЫЙ шум поворота скорости (hash по stepN):
  даёт изломы; плавные дуги — это turbAmp, не путать.
- Поля частицы: `gen` (поколение ВЕТКИ), `tier` (ярус СУБ-ЭМИТТЕРА), `stepN`
  (счётчик шагов для детерминированных кубиков), `subAcc` (аккумулятор суб-эмиссии),
  `hist` (плоский массив x,y | null).

## Путь движения (`em.path`, модуль `js/core/path.js`)

- Путь = массив УЗЛОВ `nodes[{x,y}]`, где x/y — обычные ТРЕКИ (смещения от `em.x/em.y`).
  Отсюда «анимированная mask path»: двигая ключи узлов, двигаем сам путь.
  Ключ массива именно `nodes`, а НЕ `pts`: `Model.hydrate` считает объект с полем
  `pts` «атомом» (кривая) и не дозаполняет его дефолтами — разреженные файлы сломались бы.
- `Path.bake(path, tl, ox, oy, buf)` запекает узлы в полилинию (Catmull-Rom при
  `smooth`, SUB=12 сэмплов на пролёт, кап 600) с накопленной длиной дуги;
  `Path.at(b,u)` — точка/касательная по доле длины, `Path.nearest(b,x,y)` — ближайшая
  точка + индекс пролёта (`seg`, нужен UI для вставки узла). Буфер запекания —
  СВОЙ у каждой симуляции и у панели: шарить между Engine нельзя (разное время).
- Запекание — РАЗ НА ШАГ симуляции (`sim.step`), не на частицу. Выключенный путь
  (`Path.active` false) не стоит ничего: старые эффекты попиксельно неизменны.
- ЭМИССИЯ (`mode: emit|both`): точка рождения берётся с пути, форма эмиттера
  (`em.shape`) в этой ветке НЕ участвует. Число вызовов rng на частицу в ветке пути
  ФИКСИРОВАНО — ровно 2 (доля вдоль пути + разброс поперёк), даже в режимах
  `along: even|start`, где кубик не нужен: ветвление по данным запрещено.
  `aim: tangent|normal` заменяет весь блок `em.dir` (кубик разброса — тот же один).
- ВЕДЕНИЕ (`mode: guide|both`) — только частицы яруса 0 (дети суб-эмиттера летят
  свободно): `attract` — пружина к ближайшей точке (гасится `drag`), `flow` —
  подтяжка касательной составляющей скорости к целевой (константа FLOW_K ≈ 8/с),
  `lock` — гашение поперечной скорости + притягивание позиции ПОСЛЕ интеграции
  (поэтому при lock=1 частица едет по пути, даже когда путь сам движется).
  При lock>0 на частицу приходится ДВА вызова `nearest` за шаг — это осознанно.
- `path.fast` (дефолт true) — поиск ближайшей точки в ОКНЕ ±PWIN сегментов вокруг
  подсказки прошлого шага (`p.pseg`, часть состояния частицы, -1 при рождении,
  наследуется веткой). Минимум на краю окна = подсказка протухла -> полный скан,
  поэтому на путях без самопересечений результат ПОБИТОВО совпадает с глобальным
  поиском (проверено сравнением состояний симуляции и пикселей), а ресим дешевле
  ~втрое. На самопересечениях поведение «липкое» и от глобального ОТЛИЧАЕТСЯ —
  ровно поэтому флаг лежит В ДОКУМЕНТЕ, а не в настройках редактора: иначе один
  файл давал бы разный экспортный атлас на разных машинах.
- Экстраполяция отрисовки (`ext`) идёт по скорости и с пути слегка сходит — норма.

## Суб-эмиттер (`em.sub`) — частица как эмиттер

- Отличие от `branch`: у ребёнка СВОЙ ПОЛНЫЙ блок частицы `em.sub.pt` (спрайт,
  кривые, градиент, физика, glow, режим trail) — тот же набор полей, что у `layer.pt`.
  `branch` же клонирует внешность родителя. Не дублировать одно другим.
- Ярус частицы — `p.tier` (0 — своя частица слоя, 1..maxGen — дочерние). Блок
  частицы по ярусу — `ptOf(layer, tier)`; физика хойстится ПО ЯРУСАМ (`physOf`),
  в цикле выбирается `p.tier > 0 ? ph1 : ph0`. Арифметика яруса 0 не изменилась —
  старые эффекты попиксельно идентичны (проверено сравнением состояний симуляции).
- Кубики ребёнка — СОБСТВЕННЫЙ prng (`mulberry32` от seed+stepN+индекса+salt),
  основной поток `this.rng` не трогается. Число вызовов cr() на одного ребёнка
  ФИКСИРОВАНО (8 подряд в начале) — ветвление по данным запрещено.
- Эмиссия «по жизни» — свой аккумулятор `p.subAcc` у каждой частицы (не общий
  `this.acc`); «при гибели» — выброс `sub.count` ДО splice родителя.
- `maxGen > 1` переиспользует ТОТ ЖЕ `sub.pt`, масштабируя size/life/rate через
  `genScale^(tier-1)` (массив `sc.genScale`). Отдельного блока на уровень нет.
- Каждый ярус — ОТДЕЛЬНЫЙ проход `drawPass` в engine (порядок задаёт `sub.under`),
  потому что весь хойст прохода (tex/glow/trailMode/squash) зависит от блока
  частицы. Выключенный суб-эмиттер = ровно один проход с `tierSel = -1`.
  Каждый проход обязан завершаться `ctx.setTransform(1,0,0,1,0,0)` — иначе трейлы
  второго прохода уедут на матрице спрайтов первого.
- Взрыв счётчика частиц — главный риск: `rate` умножается на число ЖИВЫХ родителей.
  Кап `sub.budget` считается по `sim.subN` (инкремент при рождении, декремент при
  гибели tier>0). Общий `MAX_PARTS` действует и здесь; валидатор предупреждает про оба.

## Спрайты (sprites.js)

- Все процедурные спрайты БЕЛЫЕ, база 128px; цвет — тонировкой
  (`source-in`) из кэша `getTinted(sig, hex)`; hex квантуется градиентом
  (`Grad.hexAt`, шаг 1/24) — иначе кэш взорвётся.
- Кэши base/tint/glow триммятся (CACHE_MAX); ключ glow включает квантованный blur.
- Вариативные фигуры (smoke/blob/shard): 4 варианта, выбор — per-particle
  (`p.vi`) либо фиксированный `sprite.p.var >= 0`.
- Новая фигура = drawer в `drawers` + запись в `S.shapeDefs` (label и tip — АНГЛИЙСКИЕ:
  label переводится в RU-словаре, tip — подсказка пикера 30–120 символов, перевод в TIPS)
  + при параметрах — `params` спека с тем же `tip` у каждого (виджеты построятся сами).
  Проверка — `node tools/i18ncheck.mjs`.
- Текстуры: реестр `S.texs` (id -> {img, dataURL, sheet}) ГЛОБАЛЬНЫЙ на сессию;
  мета в `doc.textures`, пейлоад — в реестре/файле эффекта. `Model.syncTexSheets`
  синхронизирует sheet-мету дока в реестр — звать после правок sheet.

## Типы слоёв

- `M.LAYER_TYPES` = emitter | sprite | atlas | postfx | force; шаблон типа — `M.layerTemplate(doc, type)`
  (используется в hydrate). НОВЫЙ ТИП = запись в обе эти точки, иначе hydrate
  схлопнет неизвестный type в sprite/emitter и слой потеряет дефолты.
- `atlas` (`M.newAtlas`) — тот же блок `sp` и тот же путь рендера, что у спрайта
  (engine ветвится ТОЛЬКО на emitter, остальное идёт в drawSprite — новых веток
  в engine не заводить). Разница только в дефолтах: источник — лист-текстура,
  blend normal (scale/opacity статичны у обоих). Кадр: `sp.fps > 0` — цикл по времени,
  `0` — лист растянут на окно слоя.
- `postfx` (`M.newPostFx`) — своя ветка в `Engine.render` (см. ниже): он не рисует,
  а обрабатывает пиксели. Для всего рисующего правило прежнее — новых веток в engine
  не заводить, всё идёт в drawSprite (через `Engine.drawLayer`).
- `force` (`M.newForce`) — слой-корректор ФИЗИКИ: в `Engine.render` он только
  пропускается (`continue`), вся работа идёт в симуляции (см. «Силовые поля»).
- Валидатор (tools/validate.mjs) держит свой список типов: ENUMS['layer.type']
  + выбор шаблона слоя (в ДВУХ местах: scanUnknown и checkDoc). Новый тип — добавить и туда.
- `tools/simhash.mjs` тоже строит `forceIndex` и передаёт `fc` в `ensure`: без этого
  регрессия «старые файлы не поехали» не увидела бы правок силовых полей.

## Силовые поля (слой `force`)

- Слой ничего не рисует и пикселей НЕ трогает: он добавляет ускорение частицам
  эмиттеров-адресатов ВНУТРИ симуляции. Отсюда и разделение с postfx: смаз/искажение
  размазывают готовый кадр, поле — реально гнёт траектории.
- `M.forceIndex(doc)` строит «emitterId -> {rev, list}» РАЗ НА КАДР в `Engine.render`
  (слоёв единицы) и уезжает в `Sim.ensure(layer, tl, fc)`. `fc.rev` — FNV-хэш пар
  (id, `_rev`) слоёв-полей: расхождение = reset симуляции, тот же протокол, что и
  `layer._rev`. Полей нет -> индекс `null`, весь путь идёт прежней арифметикой и
  старые файлы попиксельно неизменны.
- Solo слоёв-полей НЕ учитывается осознанно: поле ничего не рисует, и соло эмиттера
  не должно менять его физику. `forceIndex` читает `doc.layers`, а не visibleLayers.
- Поля распаковываются раз на шаг в ПЛОСКИЙ буфер `sim.fbuf` (FF_N=7 чисел на поле,
  буфер переиспользуется) — аллокаций в горячем цикле нет. Время каждого поля своё:
  местное время = `layer.start + tl - forceLayer.start`.
- Область — эллипс `(sx, sy)`; при `d >= 1` ранний выход. Направление — градиент
  нормированного расстояния (у круга = обычный радиус). Ускорение складывается с
  гравитацией ДО интегрирования, поэтому `drag` действует на него как на всё.
- Виды (`mode`, НЕ `kind` — иначе объект станет «атомом» для hydrate):
  `collapse` (к центру), `expand` (от центра), `drive` (по касательной — вихрь).
  Отрицательная сила разворачивает любой из них.
- Элементы `ff.fields` — массив, а массивы `Model.hydrate` НЕ обходит: дефолты полям
  доставляет `M.fillForceField` из `migrate()`. Новое поле поля добавлять в ОБЕ точки.

## Постэффекты (слой `postfx`)

- Слой-корректор: обрабатывает всё, что накоплено ПОД ним (индексы больше своего).
  `layer.opacity` = СИЛА эффекта, `blend`/`glowL`/`fadeOn` для него мертвы.
- Оффскрин композиции (`_post`) заводится ТОЛЬКО если `postParams()` вернул не null
  хоть для одного postfx-слоя; иначе `out === ctx` и путь рендера прежний —
  старые файлы попиксельно неизменны. Байпас (сила 0, длина 0, время вне окна)
  обязан оставаться бесплатным.
- АДРЕСАЦИЯ (`layer.targets`, общая с `force`): пусто — «всё, что ниже» (прежнее
  поведение). Непустой список ИЗОЛИРУЕТ группу: адресаты рисуются в `_grp`, эффект
  идёт по нему, результат композитится на месте корректора с его `blend` (у постэффекта
  blend мёртв ТОЛЬКО в безадресном режиме — здесь это блендинг группы, аддитивным
  слоям нужен add). Слой-адресат забирает БЛИЖАЙШИЙ сверху корректор (`postGroups`
  идёт по стеку снизу вверх); `postfx`/`force` адресатами быть не могут — это
  исключает вложенные группы и гонку за `_grp`. Байпас группу не заводит вовсе,
  и тогда адресаты рисуются обычным порядком стека.
- Один слой композиции рисует `Engine.drawLayer` (прямой путь либо оффскрин
  затухания/свечения) — им же рисуется группа. Новых копий этого кода не заводить.
- Через оффскрин идут только слои ПОД самым верхним активным БЕЗАДРЕСНЫМ постэффектом (`topPost`):
  после него оффскрин блитится в ctx и `out` возвращается на ctx. Причина — цена
  рисования в побочную канву: те же 2000 drawImage в оффскрин + блит стоят ~1.5x
  от прямых (замерено), то есть оверхед постэффекта растёт от ЧИСЛА draw-call'ов,
  а не от числа сэмплов. Пиксельная работа смаза идёт на GPU (~50 Гпикс/с, до 1024²
  её на фоне не видно) — экономить надо draw-call'ы, а не проходы.
- Смаз набирает N = 2^passes сэмплов за `passes` проходов УДВОЕНИЯ: каждый проход
  усредняет буфер с его же сдвинутой копией (шаг 1, 2, 4... сэмпла). 16 сэмплов =
  4 прохода, а не 16 отрисовок кадра. Работает потому, что сдвиг (directional) и
  «поворот+зум вокруг точки» (radial) коммутативны сами с собой.
- Усреднение ТОЧНОЕ (энергия кадра сохраняется, проверено): две отрисовки с
  `globalAlpha 0.5` в режиме `'lighter'` складывают премультиплицированные цвет и
  альфу без клампа. Тем же приёмом делается точный lerp с чистым кадром при силе < 1.
- Смаз ЦЕНТРИРОВАН вокруг чистого кадра (нулевой сэмпл сдвинут на минус половину),
  у radial зум мультипликативный, поэтому «px на краю» решается через
  `R*(sqrt(G) - 1/sqrt(G)) = len` — не заменять на наивное `1 + len/R`.
- Это ПИКСЕЛЬНЫЙ пост: направление одно на весь кадр. Смаз каждой частицы по её
  СОБСТВЕННОЙ скорости — это `pt.stretch`/`pt.alignVel` в блоке частицы, не постэффект.
- ИСКАЖЕНИЕ (`fx.effect: 'displace'`) — второй постэффект, и единственный, кто идёт
  ПО ПИКСЕЛЯМ (getImageData -> сдвиг -> putImageData), а не draw-call'ами. Держится
  дёшево тремя вещами: (1) смещение считается на РЕДКОЙ сетке (`scale/16` px) и
  тянется на пиксели, (2) обрабатывается только bbox непрозрачного кадра плюс поле
  на `amount`, (3) кадр всегда размера композиции — supersample атласа сюда не
  доходит. Интерполяция сетки — smoothstep, НЕ билинейная: у билинейной рвётся
  производная на границах ячеек и изломы вылезают сеткой складок (уже чинили).
  Тапы берутся ПРЕМУЛЬТИПЛИЦИРОВАННЫМИ, иначе по кромке альфы идёт тёмная кайма.
- ОФФСКРИНЫ `Engine.scratch` создаются с `willReadFrequently: false` — это защита от
  эвристики Chrome, а не вкусовщина. Канву, которую регулярно читают `getImageData`
  (искажение — каждый кадр), Chrome после ~800 чтений (≈50 с плейбека) молча переводит
  на CPU-растеризацию, и каждый `drawImage` GPU-оффскрина в неё (`_layFx`/`_blurFx`
  свечения, `_grp` группы) становится обратным чтением. Замерено на Nova: 16 fps -> 3.3 fps
  через ~50 с цикла, `getImageData` 9 -> 240 мс; с флагом — ровные 16–17 fps сколько угодно
  долго. Флаг работает только при СОЗДАНИИ контекста (повторный `getContext` его не меняет);
  все оффскрины одного Engine держать на одной стороне (GPU) — «смешанное» состояние и есть
  обвал. Атласная `cellCtx` наоборот `true`: там одно чтение на ячейку.
  Мерить такое в панели браузера нельзя (скрытая панель морозит rAF): headless Chrome
  `--headless=new --remote-debugging-port` + `Runtime.evaluate` через CDP даёт настоящий
  rAF на реальном GPU; профилировать `getImageData` отдельно от JS-цикла.
- ПИКСЕЛЬ-АРТ (`fx.effect: 'pixelate'`) — третий постэффект. Разрешение задаёт только
  СЕТКУ (`Model.pixelGridOf` — единственный источник правды, её же читают атлас и
  превью); «настоящий пиксель» делают четыре независимых шага: выборка блока, альфа,
  цвет, обводка. Дёшев: один GPU-даунскейл в сетку (gw x gh) -> вся пиксельная работа
  на этой мелкой сетке (64x64 = 4096 пикселей) -> один GPU-апскейл НЕАРЕСТОМ.
  `getImageData` по кадру целиком читает ТОЛЬКО режим выборки `peak`.
- РОВНЫЕ КВАДРАТЫ (`pxSnap`) — это и есть разница между «правильной» и «неправильной»
  пикселизацией: при дробном блоке (512/70 = 7.31) соседние блоки выходят 7 и 8 px и
  диагональ идёт рвано. Снап держит блок ЦЕЛЫМ, подправляя итоговое разрешение
  (70 -> 74), и пишет фактическое в инспектор. Проверяется не на глаз: все переходы
  цвета обязаны лежать на кратных bx/by (тест — скан строк и столбцов).
- 1-БИТНАЯ АЛЬФА (`pxAlpha: 'cut'`) — второе, чем пиксель-арт отличается от
  уменьшенной картинки. Порог применяется ПОСЛЕ `pxGain`: усреднение блока съедает
  однопиксельный штрих до призрака, усиление возвращает его в плотный пиксель.
- Дизеринг Байера (матрица строится рекурсивно, нормирована в ±0.5, среднее ноль —
  яркость не уезжает) считается по СЕТКЕ АРТА, не по экранным пикселям: иначе выйдет
  шум, а не пиксель-арт-узор. Тот же сдвиг идёт и в порог альфы.
- Палитры — `Model.PIXEL_PALETTES` (данные, лейблы английские); подбор ближайшего
  цвета взвешен по чувствительности глаза (g тяжелее r и b), иначе искры уезжают в синеву.
  Разбор hex и сэмплинг рампы кэшируются (`PAL_CACHE` / `RAMP_CACHE`) — в горячем цикле их нет.
- Поля искажения: `swirl` — вихрь турбулентного шума, бездивергентный, площадь
  сохраняется, дыр в массе не выбивает; `tear` — свой шум по каждой оси, рвёт резче,
  но дыры выбивает. Вихрь считается ПООКТАВНО (`AFX.turbCurl3`): если
  продифференцировать готовый fBm целиком, каждая октава входит с множителем частоты
  и мелкая забивает остальные — картинку рвёт в лапшу.
- Качество (samples/half) — поле ДОКУМЕНТА, а не настройка вьюпорта: «черновой режим
  превью» сломал бы инвариант «превью == атлас».

## Треки и кривые

- Трек = число (статика) ИЛИ `{keys:[{t,v,i:{m},o:{m}}]}`. Время ключей —
  ОТ НАЧАЛА СЛОЯ (перенос бара двигает анимацию). Цветовой трек: v = [r,g,b].
- Изинг сегмента A->B: cubic-bezier из `Track.segControls` по режимам
  `A.o.m` / `B.i.m`: lin | ease | hold | cust (h=[x,y] — нормализованная ручка,
  y может выходить за [0,1] — овершут легален).
- Кривые "за жизнь" (`Curve`) — отдельная сущность в пространстве 0..1 жизни
  частицы (Catmull-Rom, clamp v>=0). Не путать с треками.
- Градиент (`Grad`) — стопы RGB; альфа живёт в opacityOL, не в градиенте.

## Атлас (atlas.js)

- Кадры сэмплируются по ЦЕНТРАМ интервалов: `t = t0 + (i + 0.5) * step` —
  чтобы первый кадр burst-эффекта не был пустым. Не менять на сэмплинг по началу.
- НАРЕЗКА кадров (`exp.cuts`, `Atlas.cutBounds`): внутренние границы интервалов —
  ДОЛИ 0..1 между t0 и t1 (не абсолютное время: иначе правка Start/End ломала бы
  порядок узлов), длина `frames-1`, неубывающие (кламп в `cutBounds`). null или
  чужая длина = равномерно, и тогда `Atlas.centers` идёт ПРЕЖНЕЙ формулой байт в
  байт — старые файлы дают те же пиксели (проверено сравнением времён по всей
  library). Сэмплинг при любой нарезке остаётся по центрам интервалов.
- `Atlas.centers` отдаёт ещё и `bounds` (frames+1 узлов) — по ним таймлайн рисует
  голубые маркеры, а `Atlas.frameAt(ft, t)` даёт кадр по времени (плеебл-вьюпорт,
  подсветка ячейки). Смена ЧИСЛА кадров обнуляет `cuts` (globalspanel.syncFrames):
  массив привязан к числу кадров, а не к их содержимому.
- ГРАБЛЯ (уже чинили): в режиме mask НЕЛЬЗЯ заливать ячейку чёрным ДО чтения
  альфы — maskify читает альфу и превращает её в белое на чёрном. Чёрная
  заливка только на уровне итогового атласа и в режиме black.
- Supersample: рендер ячейки в 2x и даунскейл. `willReadFrequently` на cellCtx.
- ПИКСЕЛЬ-АРТ 1:1 (`exp.pixelArt`): размер ячейки даёт `Atlas.cellSize(doc, o)` —
  ячейка = сетка слоя-пикселизатора, `ss` форсится в 1, сглаживание выключается.
  Укладку кадра делает общий `Atlas.fitComp` (им же пользуется секвенция): в
  пиксель-режиме это не «вписывание», а ТОЧНАЯ ОБРАТНАЯ матрица к разгону сетки в
  движке — каждый блок композиции ложится ровно в один тексель ячейки (проверено
  сравнением всех текселей: 0 расхождений). Любой другой размер ячейки пересэмплирует
  блоки, и ровная лесенка снова поедет — ради этого галочка и существует.
  Слоя-пикселизатора в доке нет — молча падаем на cellW/cellH.
- Каждый `Atlas.build` создаёт СВОЙ Engine — не переиспользуй превью-движок.
- `Atlas.buildSequence` (PNG-секвенция) делит с атласом СЭМПЛИНГ (`Atlas.centers`)
  и весь порядок отрисовки ячейки (fit -> maskify -> даунскейл): кадр N секвенции
  ОБЯЗАН попиксельно совпадать с ячейкой N атласа при равных настройках (проверено).
  Рендер асинхронный (кадр за тик, `cancel()`), паковка — `AFX.Zip.blob` (store, без зависимостей).
  В СКРЫТОЙ вкладке `canvas.toBlob` троттлится до ~1 кадра/с — это браузер, не код.

## Документ (model.js)

- Схема: см. `docs/FORMAT.md`. Новое поле = дефолт в фабрике + дефолт в
  `Model.migrate()` (старые файлы/автосейвы обязаны открываться) — это аналог
  save-совместимости игры.
- `stripJson` вырезает ключи с префиксом `_` — runtime-состояние (`_rev`,
  `_tlOpen`) хранить только так.
- Пресеты слоёв (`layerPresets`) и заводские эффекты (fxpresets.js) строятся
  КОДОМ через фабрики (не сырым JSON) — чтобы не разъезжаться со схемой.
  Имена/лейблы — английские; лейблы переводятся в точке показа через `L()`.
